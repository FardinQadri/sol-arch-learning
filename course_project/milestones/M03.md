# M03 — The compute layer for shortly-infra

You build the third layer: the compute the app runs on. An Application Load Balancer (ALB) in the public subnets, a target group, a launch template, an Auto Scaling group in the private app subnets with a CPU target-tracking policy, and listener rules. The instances install the course's own shortly app from user data. All of it goes in one CloudFormation template, `infra/compute.yaml`.

The template costs nothing while it is only a file and the tests run. It costs money only if you deploy it: the ALB bills by the hour plus load capacity units (LCUs), each instance bills by the hour, and the ALB's public IPv4 addresses bill by the hour too. See `DEPLOY.md` before you deploy.

Do this milestone in week 03, after the compute and scaling notes and drills.

## What the tests rely on

The tests look for exact names. Use these.

| What | Value |
|---|---|
| Template file | `infra/compute.yaml` |
| Parameters | `Prefix` (default `shortly`), `Env` (`lab` or `prod`), `InstanceType` (default `t4g.small`, with `AllowedValues`), `ImageId` (an SSM-typed parameter, see M03.1) |
| Condition | `IsProd`: true when `Env` is `prod` |
| `LoadBalancer` | `AWS::ElasticLoadBalancingV2::LoadBalancer` |
| `AppTargetGroup` | `AWS::ElasticLoadBalancingV2::TargetGroup` |
| `HttpListener` | `AWS::ElasticLoadBalancingV2::Listener` |
| `HealthzRule`, `ApiRule` | `AWS::ElasticLoadBalancingV2::ListenerRule` |
| `AppLaunchTemplate` | `AWS::EC2::LaunchTemplate`, name `${Prefix}-app` |
| `AppAutoScalingGroup` | `AWS::AutoScaling::AutoScalingGroup` |
| `CpuTargetTracking` | `AWS::AutoScaling::ScalingPolicy` |

The template imports six values from the earlier stacks, with `!ImportValue` and the export names of `Prefix=shortly`:

| Import | Made by | Used for |
|---|---|---|
| `shortly-vpc-id` | M02 | the target group's VPC |
| `shortly-public-subnet-ids` | M02 | the load balancer's subnets |
| `shortly-app-subnet-ids` | M02 | the Auto Scaling group's subnets |
| `shortly-alb-sg-id` | M02 | the load balancer's security group |
| `shortly-app-sg-id` | M02 | the instances' security group |
| `shortly-app-instance-profile` | M01 | the instances' IAM role |

The tests fill in `Prefix=shortly`, account `111122223333` and region `us-east-1`. They check `Env=prod` and `Env=lab` separately.

## M03.1 — the load balancer and the target group

The ALB takes requests from the internet and forwards them to the app. The test checks:

- parameters `Prefix` (default `shortly`), `Env` (`AllowedValues` `lab` and `prod`), `InstanceType` (default `t4g.small`, with `AllowedValues`) and `ImageId` exist;
- `ImageId` has the type `AWS::SSM::Parameter::Value<AWS::EC2::Image::Id>` and the default `/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-arm64`: Amazon Linux 2023 for Graviton (arm64). CloudFormation asks Systems Manager for the newest AMI id each time the stack is created or updated, so you never hard-code an AMI id;
- `LoadBalancer` is an `application` load balancer, `internet-facing`, in the public subnets (`!Split [',', !ImportValue …-public-subnet-ids]`) with the ALB security group;
- `AppTargetGroup` is HTTP on port 8000 (where the app listens), in the imported VPC, target type `instance`, health check path `/healthz`, and it accepts only HTTP code `200`;
- the target group's deregistration delay is 60 seconds or less. The default is 300 seconds, so every scale-in would wait five minutes for an app whose requests take milliseconds.

The AMI parameter:

```yaml
ImageId:
  Type: AWS::SSM::Parameter::Value<AWS::EC2::Image::Id>
  Default: /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-arm64
```

The deregistration delay is a target group attribute: `TargetGroupAttributes` is a list of `Key` and `Value` pairs, and the value is a string.

## M03.2 — the launch template

The launch template says what every instance looks like. The test reads the template, not any instance (see the note after M03.6). It checks:

- `LaunchTemplateName` is `${Prefix}-app`;
- `ImageId` is `!Ref ImageId` and `InstanceType` is `!Ref InstanceType`;
- every allowed instance type, and the default, is a Graviton type (the AMI is arm64, so an x86 type would not boot). The test decodes the name, so `t4g.small` passes and `t3.small` does not;
- IMDSv2 is required (`HttpTokens: required`), the metadata endpoint is `enabled`, and `HttpPutResponseHopLimit` is 1;
- the instance profile comes from M01 (`IamInstanceProfile: {Name: …}`) and the security group from M02 (`SecurityGroupIds`);
- there is no `KeyName` (use Session Manager, not SSH keys) and no `AssociatePublicIpAddress`: the instances are private and reach the internet through NAT.

The metadata block:

```yaml
MetadataOptions:
  HttpTokens: required
  HttpPutResponseHopLimit: 1
  HttpEndpoint: enabled
```

With IMDSv1 (`HttpTokens: optional`) one forged request through the app can read the instance role's credentials with a single GET. IMDSv2 needs a session token first.

## M03.3 — user data that installs the app

User data is a script that cloud-init runs once, at the first boot. Yours installs the shortly app and runs it as a systemd service. The test decodes your user data and checks that:

- it starts with `#!/bin/bash`;
- it contains every non-blank line of `app/app.py`, unchanged: you write the file with a heredoc (`cat > /opt/shortly/app.py <<'EOF'` … `EOF`) and paste the app between the markers;
- it runs the app as a service: a unit file with a `[Service]` section, `ExecStart=`, `Environment=PORT=8000` and `Restart=always`, then `systemctl enable --now shortly`;
- the script is at most 16,384 bytes (16 KB) before base64. The app is well below that.

The skeleton, with the app left out:

```yaml
UserData:
  Fn::Base64: |
    #!/bin/bash
    set -euo pipefail
    useradd --system --no-create-home shortly || true
    mkdir -p /opt/shortly
    cat > /opt/shortly/app.py <<'EOF'
    # … paste app/app.py here, unchanged …
    EOF
    # … write /etc/systemd/system/shortly.service the same way, then:
    systemctl daemon-reload
    systemctl enable --now shortly
```

Every line of the pasted app must be indented by the same amount as the script around it. YAML removes that indentation in a block scalar (`|`), so the file on the instance is exactly `app/app.py`. This form has no `!Sub`, because the script has no `${…}` variables. If you ever need `${AWS::Region}` in the script, write `!Base64 !Sub |` instead. Then the script must not contain the two characters `${` anywhere else, or `!Sub` tries to read them as variables. The app does not contain them.

## M03.4 — the Auto Scaling group and its scaling policy

The Auto Scaling group keeps the right number of healthy instances running and replaces the ones that die. The test checks:

- sizes by environment: `prod` has `MinSize` 2 and `MaxSize` 6 (two instances, so one AZ can fail), `lab` has 1 and 2. Use `!If [IsProd, …, …]`;
- there is no `DesiredCapacity`: the group starts at `MinSize` and the scaling policy then owns the number;
- `HealthCheckType: ELB` and a `HealthCheckGracePeriod` between 60 and 600 seconds;
- the launch template is `!Ref AppLaunchTemplate` with `Version: !GetAtt AppLaunchTemplate.LatestVersionNumber`, the target group is in `TargetGroupARNs`, and the group lives in the private app subnets (`VPCZoneIdentifier` from `!Split [',', !ImportValue …-app-subnet-ids]`);
- a `Name` tag with value `${Prefix}-app` and `PropagateAtLaunch: true`, so the instances carry it;
- `CpuTargetTracking` is a `TargetTrackingScaling` policy on `AppAutoScalingGroup`, with the predefined metric `ASGAverageCPUUtilization` and a `TargetValue` between 40 and 70;
- the course's scaling model, given your numbers, adds instances at 100 % CPU, never goes below `MinSize` and never grows past `MaxSize`.

## M03.5 — the listener and path-based rules

The listener is the ALB's front door. The test checks:

- `HttpListener` on the load balancer, port 80, protocol HTTP, default action: forward to `AppTargetGroup`;
- there is no HTTPS listener yet. It needs a certificate, which milestone M07 adds;
- `HealthzRule` has priority 10 and `ApiRule` priority 20 (the lowest number is checked first, and no two rules share a number);
- the course's load balancer model, given your rules, answers `GET /healthz` with a fixed-response 404, forwards `POST /api/links` to the target group, and also forwards a short link such as `/Ab3dE9x` (the default action).

`/healthz` is for the target group's health checks. Those go straight from the load balancer to the instances and never pass through listener rules, so the internet gets a 404 and the health checks still work. One rule as an example:

```yaml
HealthzRule:
  Type: AWS::ElasticLoadBalancingV2::ListenerRule
  Properties:
    ListenerArn: !Ref HttpListener
    Priority: 10
    Conditions:
      - {Field: path-pattern, PathPatternConfig: {Values: [/healthz]}}
    Actions:
      - Type: fixed-response
        FixedResponseConfig: {StatusCode: '404', ContentType: text/plain, MessageBody: not found}
```

`ApiRule` has the same shape. Its path pattern is `/api/*` and its action forwards to `AppTargetGroup`.

## M03.6 — exports and the whole layer

Later stacks (edge, monitoring) import the compute layer's values. The test checks that the template has these Outputs, each with an export named `${Prefix}-…`:

| Output | Export name (Prefix `shortly`) | Value |
|---|---|---|
| `AlbDnsName` | `shortly-alb-dns-name` | the DNS name of `LoadBalancer` (`!GetAtt LoadBalancer.DNSName`) |
| `AlbArn` | `shortly-alb-arn` | the ARN of `LoadBalancer` (`!Ref LoadBalancer`) |
| `AppTargetGroupArn` | `shortly-app-tg-arn` | `AppTargetGroup` (`!Ref`) |
| `AppAsgName` | `shortly-app-asg-name` | `AppAutoScalingGroup` (`!Ref`) |

Then it checks that:

- `cfn-lint` finds no errors;
- the IAM, network and compute stacks deploy in moto one after the other, each with status `CREATE_COMPLETE`, for `Env=prod` and `Env=lab`. There is one Auto Scaling group with two instances in prod and one in lab, with health check type `ELB`; one target group with health check path `/healthz`; one load balancer in two Availability Zones;
- the latest version of the launch template says `HttpTokens: required`.

### Why some checks read the template, not the deployed stack

Moto, the offline AWS, stores launch templates and Auto Scaling groups, but it does not run scaling policies and it does not apply a launch template's settings (IMDSv2, instance profile) to the instances it starts. A test that looked at instances would pass a template that says `HttpTokens: optional`, and a deploy would pass a template with no scaling policy at all. So those checks read your template (or the stored launch template version) instead. In real AWS the settings reach the instances; the test only needs to see the right words in the right place.

## Hints (read only when stuck)

- Why `HealthCheckType: ELB`? The default health check is the EC2 status check, which only sees a dead machine. An app that crashed on a healthy machine stays "healthy" and keeps getting traffic. With ELB checks, the group replaces any instance that fails the target group's `/healthz` check.
- The grace period is the time a new instance is left alone before its health checks count. Boot, user data and the first healthy checks take a minute or two, so a very short period would kill instances that are still starting, and 600 only delays replacing a broken one. Something between 120 and 300 is reasonable. (The ALB's own defaults: a check every 30 seconds, healthy after 5 passes, unhealthy after 2 failures.)
- `!GetAtt AppLaunchTemplate.LatestVersionNumber` makes the group point at a specific version number. When you edit the launch template, CloudFormation creates a new version, the number changes, and the group is updated to launch new instances from it. Instances already running keep the old version until they are replaced (an instance refresh rolls them, note 04).
- `Subnets: !Split [',', !ImportValue {'Fn::Sub': '${Prefix}-public-subnet-ids'}]` turns the comma-separated export back into a list. An `!ImportValue` whose name needs `!Sub` takes the long form `{'Fn::Sub': …}` in short YAML.
- If you use `!Sub` for the user data, a `${` in the app would be read as a variable and break the stack. The shortly app has none, so plain `Fn::Base64: |` is enough.
- User data must be at most 16 KB before base64, and the test counts bytes. Do not add large files to the script.
- The test finds the app lines by exact text. A tab instead of spaces, a trimmed trailing space, or a wrong indentation level will show up as a missing line.
- Why hide `/healthz`? It is for the load balancer, not for the public. A visible health endpoint tells attackers which software runs and whether it is up.
- `Env` and `Prefix` must be used somewhere or `cfn-lint` warns. Use `Prefix` in names and tags.
- When a test fails, read its message first. It names the resource or the value that went wrong.

## Why this matters in the exam

- **ALB vs NLB:** an ALB works at layer 7: it routes by path, host and header, and sends health checks to a path. Choose a Network Load Balancer for TCP/UDP, static IPs or very high connection rates. A target group is where the instances register.
- **Launch templates:** they are the way to describe instances for Auto Scaling, and they have versions. Launch configurations are retired for new accounts: they can no longer create them (changed, 2024-10-01). Choose a launch template.
- **ELB health checks:** with a load balancer in front, set the group's health check type to ELB. The grace period prevents a slow-booting instance from being killed before it is ready.
- **Target tracking:** pick a metric and a target value, and Auto Scaling does the arithmetic. It is the simplest policy and the usual exam answer for "keep CPU near 50 %".
- **Two AZs:** an Auto Scaling group across two subnets in different AZs survives the loss of one. The minimum of 2 in prod is for that.
- **IMDSv2:** require the session token (`HttpTokens: required`) to protect instance role credentials from request-forgery bugs. Prefer Session Manager to SSH keys and open ports.
- **Cost:** an ALB bills per hour plus LCUs, instances per second, and every public IPv4 address per hour. Graviton instances cost up to 20 % less than comparable x86 ones.
