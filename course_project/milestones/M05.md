# M05 — The data tier for shortly-infra

You build the fifth layer: the data. Shortly uses three stores, because it has three different jobs. **PostgreSQL on RDS** holds links and users (relational data that needs transactions). A **Valkey cache** (an ElastiCache replication group) answers hot redirects from memory. **DynamoDB** holds the daily click counts (key-value, write-heavy). All of it goes in one CloudFormation template, `infra/data.yaml`. Redis OSS works the same way as Valkey here; the course uses Valkey because its node price is lower (illustrative, see `docs/facts.md`).

This is the most expensive layer so far when it is deployed. The RDS instance and the cache nodes bill by the hour even with no traffic, and Multi-AZ doubles the database price. The template costs nothing while it is only a file and the tests run. See `DEPLOY.md` before you deploy.

Do this milestone in week 05, after the database and caching notes and drills.

The tests look for exact names. Use these.

| What | Value |
|---|---|
| Template file | `infra/data.yaml` |
| Parameters | `Prefix` (default `shortly`), `Env` (`AllowedValues` `lab` and `prod`) |
| Condition | `IsProd`: true when `Env` is `prod` |

| `Cache` | `AWS::ElastiCache::ReplicationGroup` |
| `ClicksTable` | `AWS::DynamoDB::Table` |

The template imports three values from M02 with `!ImportValue`, built with `!Sub '${Prefix}-…'` (an `!ImportValue` whose name needs `!Sub` takes the long form `{'Fn::Sub': …}`):

| Import | Used for |
|---|---|
| `shortly-data-subnet-ids` | both subnet groups (one comma separated string: wrap it in `!Split [',', …]`) |
| `shortly-db-sg-id` | the database's security group |
| `shortly-cache-sg-id` | the cache's security group |

The template has six Outputs, each with an export. They are listed in M05.6. The tests also need a `README.md` section called `## Data tier` (M05.5).

The tests fill in `Prefix=shortly`, account `111122223333` and region `us-east-1`. They check `Env=prod` and `Env=lab` where it matters.

### Why most checks read the template

Moto, the offline AWS, does not create ElastiCache or Secrets Manager resources from CloudFormation, and it drops several database and table settings. It cannot answer `!GetAtt Database.MasterUserSecret.SecretArn` either. A test that looked at the deployed result would pass a template with no cache at all. So most checks read your template, and the secret policy is checked with the course's policy evaluator. The deploy test removes the cache types and the secret from the template, gives moto a literal for the secret ARN, and checks only what moto really creates: the database engine, encryption, Multi-AZ, port and subnets, the table's keys and billing mode, and the stack outputs. In real AWS every setting takes effect.

## M05.1 — the database and its subnet group

RDS needs to know which subnets, so which Availability Zones, it may use. That is a DB subnet group. The test checks that:

- parameters `Prefix` (default `shortly`) and `Env` (`AllowedValues` `lab` and `prod`) exist, and condition `IsProd` exists;
- `DbSubnetGroup` has a `DBSubnetGroupDescription` and `SubnetIds` from the imported data subnets (inside `!Split`). The data subnets have no route to the internet;
- `Database` is `Engine: postgres` with an `EngineVersion` that starts with `17.` (the reference uses `'17.9'`; quote it so YAML keeps a string);
- `DBInstanceClass` is `db.m7g.large` in prod and `db.t4g.micro` in lab;
- `AllocatedStorage: 20` (GiB, the gp3 minimum), `StorageType: gp3`, `Port: 5432`;
- `StorageEncrypted: true`. You can only choose encryption when a database is created;
- `MasterUsername: shortly`, **no** `MasterUserPassword`, and `ManageMasterUserPassword: true`. RDS then creates the password in Secrets Manager and can rotate it. No person and no template ever sees it;
- `PubliclyAccessible: false`;
- `DBSubnetGroupName: !Ref DbSubnetGroup`, and `VPCSecurityGroups` is the imported database security group. Without it, RDS attaches the VPC's default group.

The credential lines:

```yaml
MasterUsername: shortly
ManageMasterUserPassword: true
```

## M05.2 — backups, Multi-AZ and protection from deletion

Prod and lab differ here. The test renders the template for both. It checks that:

- `MultiAZ` is `true` in prod and `false` in lab. Multi-AZ keeps a synchronous standby in another zone and fails over by itself (typically 60 to 120 seconds). It is for availability, not for extra read capacity;
- `BackupRetentionPeriod` is at least 7 in prod and at least 1 in lab, and never above 35. The reference uses 7 and 1. `0` would switch automated backups off, and point-in-time recovery with them;
- `DeletionProtection` is `true` in prod and `false` in lab;
- `CopyTagsToSnapshot: true` in both;
- `Database` has `DeletionPolicy: Snapshot` and `UpdateReplacePolicy: Snapshot`, both next to `Type`, not under `Properties`. Deleting the stack, or a change that replaces the instance, then takes a final snapshot.

One property in the `!If` pattern:

```yaml
MultiAZ: !If [IsProd, true, false]
```

## M05.3 — the app's access to the database secret

The app needs the database password at run time. RDS creates a secret for it, and names it `rds!db-…`. M01's policy only allows secrets named `shortly/db-*`, so the app role cannot read the RDS secret yet. You add a policy in the data stack. The test renders `AppDbSecretPolicy` and asks the course's policy evaluator. It checks that:

- the policy is attached to the existing role by name: `Roles: [!Sub '${Prefix}-app']`, and it has a `PolicyName`;
- it has exactly one statement: `Effect: Allow`, `Action: secretsmanager:GetSecretValue`, and `Resource: !GetAtt Database.MasterUserSecret.SecretArn`. Never `'*'`;
- the app role (M01's policies together with this one) may read the secret, and this policy alone is enough;
- through this policy the app may not read another secret, and may not put, delete or rotate this one;
- the M01 permissions boundary still allows the read. The boundary caps what any grant can give, and the grant has to stay inside it.

The statement:

```yaml
Statement:
  - Sid: ReadManagedDbSecret
    Effect: Allow
    Action: secretsmanager:GetSecretValue
    Resource: !GetAtt Database.MasterUserSecret.SecretArn
```

Because the stack now creates an IAM policy, it needs a capability flag when you deploy it (see `DEPLOY.md`).

## M05.4 — the cache

A redirect is a read of one small value. A cache in front of PostgreSQL answers it from memory in well under a millisecond. The test checks that:

- `CacheSubnetGroup` has a `Description` and the imported data subnets, and `Cache` uses it with `CacheSubnetGroupName: !Ref CacheSubnetGroup`;
- `Cache` is a replication group with `Engine` `valkey` (`redis` is accepted too);
- `CacheNodeType` is `cache.m7g.large` in prod and `cache.t4g.micro` in lab;
- `NumCacheClusters` is 2 in prod (a primary and one replica in another zone) and 1 in lab;
- `AutomaticFailoverEnabled` and `MultiAZEnabled` are both `true` in prod and `false` in lab. When failover is on, the group needs at least 2 nodes;
- `TransitEncryptionEnabled: true` and `AtRestEncryptionEnabled: true` in both environments;
- `SecurityGroupIds` is the imported cache security group (it lets only the app tier reach port 6379).

## M05.5 — the clicks table and the README

`ClicksTable` holds one item per short code per day. The test checks that:

- `TableName` is `${Prefix}-clicks-daily`. The M01 policies already name this table;
- `BillingMode: PAY_PER_REQUEST`, and no `ProvisionedThroughput`. Click traffic is spiky and unknown;
- `AttributeDefinitions` are `code` (S) and `day` (S); `KeySchema` is `code` as HASH and `day` as RANGE;
- point-in-time recovery is on (`PointInTimeRecoverySpecification`);
- TTL is on, on the attribute `expires_at` (`TimeToLiveSpecification`, `Enabled: true`). Old counters are then deleted for free;
- `DeletionProtectionEnabled` is `true` in prod and `false` in lab;
- `DeletionPolicy: Retain` and `UpdateReplacePolicy: Retain`. Click history must outlive the stack.

The README test reads `README.md` in your repo. It needs a `## Data tier` section that:

- explains why each store: PostgreSQL (or "Postgres") for links and users, Valkey (or Redis) for hot redirects, DynamoDB for click counts;
- states the clicks table's monthly on-demand cost as a number with two decimals. The workload is 30 million writes of 0.5 KB and 60 million eventually consistent reads of 1 KB per month, one month. Work it out with the course's DynamoDB model (`awslib` `dynamo.monthly_cost_on_demand`): a 0.5 KB write rounds up to 1 write unit, a 1 KB eventually consistent read is 0.5 read unit, and you multiply by the price per million units from `docs/facts.md` (0.625 USD per million writes, 0.125 USD per million reads, illustrative). Storage and backups are not included.

## Hints (read only when stuck)

- Why `ManageMasterUserPassword`? A password in the template ends up in git and in CloudFormation. With this flag RDS keeps the password in Secrets Manager and rotates it; you only grant read access to the secret.
- Port 5432 is PostgreSQL's port. The M02 database security group allows 5432 from the app tier only, so set it explicitly.
- Failover promotes a replica, so a replication group with failover on needs at least two nodes. `cfn-lint` does not catch this; CloudFormation fails at deploy time. The test does catch it.
- `DeletionPolicy: Snapshot` keeps a copy of the data when the stack goes; `Retain` keeps the resource itself. A database gets a snapshot; the clicks table is simply kept.
- Point-in-time recovery lets you restore a DynamoDB table to any second in its retention window. TTL needs a number attribute holding epoch seconds.
- An `EngineVersion` that RDS does not offer fails at deploy time. Use `'17.9'` or another current 17.x, and quote it.
- `Env` and `Prefix` must be used somewhere or `cfn-lint` warns.
- When a test fails, read its message first. It names the resource or the value that went wrong.

## Why this matters in the exam

- **Multi-AZ is for availability, read replicas are for read scaling.** The standby serves no reads. Failover is automatic and changes the DNS record.
- **Backups and PITR:** automated backups (retention 0 to 35 days; 0 means off) plus transaction logs give point-in-time restore. Snapshots you take yourself stay until you delete them.
- **Encryption at creation:** you choose RDS encryption when the database is created. It covers storage, backups, snapshots and replicas.
- **Managed secrets:** `ManageMasterUserPassword` keeps the password in Secrets Manager and can rotate it. Grant access to the one secret, not `*`.
- **Caching:** a cache in front of a database cuts read load and latency. Replicas plus automatic failover give the cache high availability; encryption in transit and at rest are separate switches.
- **DynamoDB:** on-demand for unknown, spiky traffic; provisioned bills every hour used or not. Partition key plus sort key shapes the queries. PITR protects against mistakes, TTL deletes for free.
- **Cost:** RDS and cache nodes bill by the hour. db.t4g.micro is about 0.016 USD/hour Single-AZ and 0.032 Multi-AZ; Valkey cache.t4g.micro about 0.0128 USD/hour against 0.016 for Redis OSS (all illustrative, see `docs/facts.md`).
