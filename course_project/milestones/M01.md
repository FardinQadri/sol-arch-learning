# M01 — IAM baseline for shortly-infra

You build the first layer of the shortly infrastructure: every IAM role the app will need, written as one CloudFormation template. Nothing in this layer costs money.

Do this milestone in week 01, after the IAM notes and drills.

## Step 0 — your repo (once)

You do this only for M01. Later milestones reuse the same repo.

1. Make the repo folder and start git:

   ```bash
   mkdir ~/code/shortly-infra
   cd ~/code/shortly-infra
   git init
   ```

2. Create `README.md`. One paragraph is enough: shortly is the URL shortener from the Flask course, and this repo holds its AWS infrastructure as CloudFormation.
3. Create `.gitignore` with these lines:

   ```
   .venv/
   __pycache__/
   .pytest_cache/
   ```

4. From the course folder, copy the tests and tools into your repo:

   ```bash
   python course_project/tools/start_milestone.py 1 --repo ~/code/shortly-infra
   ```

5. Run the tests from inside your repo, with the course venv's Python:

   ```bash
   cd ~/code/shortly-infra
   <course>/.venv/Scripts/python.exe run_milestone.py 1
   ```

   Replace `<course>` with the path to the course folder. At the start you will see `0/6 steps green`. That is expected.

Do not edit anything under `tests/`. The course overwrites it every milestone.

## What the tests rely on

The tests look for exact names. Use these.

| What | Value |
|---|---|
| Template file | `infra/iam.yaml` |
| Parameter files | `params/lab.json` and `params/prod.json` |
| Parameters | `Prefix` (default `shortly`) and `Env` (`lab` or `prod`) |
| `AppBoundary` | `AWS::IAM::ManagedPolicy`, name `${Prefix}-boundary` |
| `AppRole` | `AWS::IAM::Role`, name `${Prefix}-app` |
| `AppInstanceProfile` | `AWS::IAM::InstanceProfile`, name `${Prefix}-app` |
| `ConsumerRole` | `AWS::IAM::Role`, name `${Prefix}-click-consumer` |
| `DeployerRole` | `AWS::IAM::Role`, name `${Prefix}-deployer` |
| `AuditorRole` | `AWS::IAM::Role`, name `${Prefix}-auditor` |

Those first column names are the logical ids: the keys under `Resources:`. The tests find your resources by them.

The tests fill in `Prefix=shortly` and `Env=prod`, and they use account `111122223333` and region `us-east-1`.

## M01.1 — repo skeleton and parameters

The test checks:

- the repo has `infra/`, `params/`, `README.md` and `.gitignore`;
- `.gitignore` lists `.venv` and `__pycache__`;
- `params/lab.json` is exactly `{"Prefix": "shortly", "Env": "lab"}`, and `params/prod.json` is the same with `"prod"`;
- `infra/iam.yaml` loads, has the two parameters below, and `cfn-lint` finds no errors.

Start `infra/iam.yaml` with a version line, a description, and this Parameters block:

```yaml
Parameters:
  Prefix:
    Type: String
    Default: shortly
  Env:
    Type: String
    AllowedValues: [lab, prod]
```

Every stack in this course will take these two parameters. `Prefix` keeps names unique, and `Env` lets you tell lab from prod.

## M01.2 — the app role and instance profile

The app runs on EC2. Give it the permissions it needs and nothing more. The test checks:

- `AppRole` is named `shortly-app` and only the EC2 service can assume it (not Lambda, not an account root);
- `AppInstanceProfile` holds `AppRole` and is also named `shortly-app`;
- the app is allowed exactly these actions:
  - read the database secret (`secretsmanager:GetSecretValue` on `shortly/db-…`);
  - `dynamodb:GetItem` and `dynamodb:Query` on the `shortly-clicks-daily` table;
  - `s3:GetObject` and `s3:PutObject` on the `uploads/` prefix of the `shortly-assets-<account>` bucket;
  - `sqs:SendMessage` on the `shortly-clicks` queue;
  - `logs:PutLogEvents` in the `/shortly/app` log group;
  - `cloudwatch:PutMetricData`, only for the namespace `Shortly`.

The trust policy says who may assume the role. For EC2 it looks like this:

```yaml
AssumeRolePolicyDocument:
  Version: '2012-10-17'
  Statement:
    - Effect: Allow
      Principal: { Service: ec2.amazonaws.com }
      Action: sts:AssumeRole
```

Each permission is a statement in a policy. Here is one example, for the queue. Write the others in the same shape, each with its own actions and its own resource ARN:

```yaml
- Effect: Allow
  Action: sqs:SendMessage
  Resource: !Sub 'arn:${AWS::Partition}:sqs:${AWS::Region}:${AWS::AccountId}:${Prefix}-clicks'
```

Use `Policies:` (inline policies) on the role.

## M01.3 — the Lambda execution role

Later, a Lambda function reads click events from a queue and writes daily totals. This is its role. The test checks:

- `ConsumerRole` is named `shortly-click-consumer`;
- only the Lambda service can assume it (not EC2);
- it may `sqs:ReceiveMessage`, `sqs:DeleteMessage` and `sqs:GetQueueAttributes` on the `shortly-clicks` queue;
- it may `dynamodb:UpdateItem` on the `shortly-clicks-daily` table;
- it may write to its log group `/aws/lambda/shortly-click-consumer`;
- it may not send to the queue, and may not delete items from the table.

## M01.4 — the deployer role and the permissions boundary

A permissions boundary is a ceiling. A role can never do more than its boundary allows, even if its own policy says more. The test checks:

- `AppBoundary` is a managed policy named `shortly-boundary`;
- `AppRole` and `ConsumerRole` both set `PermissionsBoundary: !Ref AppBoundary`;
- the boundary allows the services shortly uses, but not IAM actions such as `iam:CreateUser`. The test gives a role full admin rights, puts your boundary on top, and checks that `iam:CreateUser` is still blocked while `s3:GetObject` still works;
- `DeployerRole` may create roles (`iam:CreateRole`) only when:
  - the role name starts with `shortly-`, and
  - the request sets the boundary `shortly-boundary` (use the condition key `iam:PermissionsBoundary`);
- the deployer is explicitly denied removing a role's boundary (`iam:DeleteRolePermissionsBoundary`) and changing the boundary policy (`iam:CreatePolicyVersion` on it). An explicit deny always wins;
- `iam:PassRole` is allowed only when the role is passed to EC2 or Lambda (condition key `iam:PassedToService`);
- the deployer may use CloudFormation only on stacks named `shortly-*`;
- humans can assume the deployer only with MFA, and only from your own account (`aws:MultiFactorAuthPresent`).

The deployer also needs real permissions to build the later layers. Keep them limited to what the tests and the course need. The checks in M01.6 forbid `Action: '*'`.

## M01.5 — the auditor role

An auditor can look at everything but change nothing. The test checks:

- `AuditorRole` is named `shortly-auditor`;
- it attaches the AWS managed policy `ReadOnlyAccess` (or `SecurityAudit`) and has no inline policies;
- `MaxSessionDuration` is `3600` seconds (one hour);
- a person from your account can assume it only when `aws:MultiFactorAuthPresent` is true. No MFA information at all must also fail.

## M01.6 — the whole layer

The last step checks the template as a whole. The test checks:

- no statement in `AppRole`, `ConsumerRole` or `DeployerRole` has `Action: '*'`;
- `Resource: '*'` appears only on `cloudwatch:PutMetricData`, and only together with a `Condition`;
- the app role is not allowed any of ten dangerous actions. Among them: deleting the DynamoDB table, writing to it with `PutItem`, deleting S3 objects, reading outside `uploads/`, receiving from the queue, reading someone else's secret, `iam:CreateUser`, and sending metrics to the `AWS/EC2` namespace;
- the template deploys in moto (a fake AWS) with status `CREATE_COMPLETE`, and the four roles exist, with `shortly-app` carrying the boundary.

If an earlier step is already green, this step mostly confirms you did not grant too much. Tighten any statement that is too wide.

## Hints (read only when stuck)

- `cloudwatch:PutMetricData` cannot name a resource, so it needs `Resource: '*'`. Limit it with a condition instead: `StringEquals` on `cloudwatch:namespace` with the value `Shortly`.
- Secrets Manager adds a random 6-character suffix to a secret's ARN (`…:secret:shortly/db-AbCdEf`). End your resource with `-??????` so it matches.
- Build ARNs with `!Sub 'arn:${AWS::Partition}:service:${AWS::Region}:${AWS::AccountId}:…'`. For S3 there is no region or account in the ARN: `arn:${AWS::Partition}:s3:::bucket/prefix/*`.
- The boundary's ARN is `arn:${AWS::Partition}:iam::${AWS::AccountId}:policy/${Prefix}-boundary`. Use it in the deployer's condition.
- `cfn-lint` warns about parameters that nothing uses. Tag your roles with `project` and `env` (`!Ref Env`) so `Env` is used.
- A role with a name needs the `CAPABILITY_NAMED_IAM` flag when it is deployed. The moto test handles this for you.
- When a test fails, read its message first. It names the exact action and ARN that went wrong.

## Why this matters in the exam

- **Delegation with boundaries:** a boundary lets a team create roles safely, because those roles can never exceed the ceiling.
- **MFA on human roles:** trust policies can require `aws:MultiFactorAuthPresent`.
- **Instance profiles, not keys:** EC2 gets credentials from a role. Never put access keys on an instance.
- **Least privilege:** name the actions and the resources. An explicit deny beats any allow.
