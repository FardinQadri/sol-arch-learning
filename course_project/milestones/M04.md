# M04 — The storage layer for shortly-infra

You build the fourth layer: the storage. Two S3 buckets. The **assets bucket** holds what users upload (logos, images). The **logs bucket** is ready for the load balancer's access logs (you switch logging on for the M03 load balancer in a later milestone; this one prepares the bucket and its permissions). Both are private, both have bucket policies, and both have lifecycle rules so that old data does not pile up and bill you forever. All of it goes in one CloudFormation template, `infra/storage.yaml`.

Storage costs money only for what is stored (and for requests). A test deploy with a few bytes in it costs a fraction of a cent. See `DEPLOY.md` before you deploy.

Do this milestone in week 04, after the storage notes and drills.

## What the tests rely on

The tests look for exact names. Use these.

| What | Value |
|---|---|
| Template file | `infra/storage.yaml` |
| Parameters | `Prefix` (default `shortly`), `Env` (`AllowedValues` `lab` and `prod`) |
| Condition | `IsProd`: true when `Env` is `prod` |
| `AssetsBucket` | `AWS::S3::Bucket`, name `${Prefix}-assets-${AWS::AccountId}` |
| `AssetsBucketPolicy` | `AWS::S3::BucketPolicy` on `AssetsBucket` |
| `LogsBucket` | `AWS::S3::Bucket`, name `${Prefix}-logs-${AWS::AccountId}` |
| `LogsBucketPolicy` | `AWS::S3::BucketPolicy` on `LogsBucket` |

The template imports one value from M01 with `!ImportValue`: the app role's ARN, export name `shortly-app-role-arn` (build it with `!Sub '${Prefix}-app-role-arn'`; an `!ImportValue` whose name needs `!Sub` takes the long form `{'Fn::Sub': …}`). The assets bucket policy lets that role in.

Ids the tests look for inside the template: statements `AllowAppUploads` and `DenyInsecureTransport` (assets policy), `AllowAlbLogDelivery` and `DenyInsecureTransport` (logs policy), and the lifecycle rules `noncurrent-versions` (assets bucket) and `alb-logs` (logs bucket).

The template has four Outputs, each with an export. They are listed in M04.5.

The tests fill in `Prefix=shortly`, account `111122223333` and region `us-east-1`. They check `Env=prod` and `Env=lab` where it matters.

### Why most checks read the template

Moto, the offline AWS, keeps only three things of a bucket made by CloudFormation: its name, its tags and its default encryption. It drops versioning, Block Public Access, ownership controls and lifecycle rules, and it skips bucket policies. A test that looked at the deployed bucket would pass an empty template. So the tests read your template, and the bucket policies and lifecycle rules are checked with the course's own models (the policy evaluator and the lifecycle model). Only the names, the encryption and the outputs are checked on the moto deploy. In real AWS every setting takes effect; the tests only need to see the right words in the right place.

## M04.1 — the assets bucket

The assets bucket is where the app puts uploads. The test checks that:

- parameters `Prefix` (default `shortly`) and `Env` (`AllowedValues` `lab` and `prod`) exist;
- `AssetsBucket` is named `${Prefix}-assets-${AWS::AccountId}`. The M01 app role and the M02 S3 endpoint policy already expect this name, and the account id keeps it globally unique (bucket names are unique across all AWS accounts);
- versioning is `Enabled`. A delete then only adds a delete marker, and an overwrite keeps the old version, so you can undo both;
- default encryption is SSE-KMS (`aws:kms`) with `BucketKeyEnabled: true`, and **no** `KMSMasterKeyID`: S3 then uses the AWS managed key `aws/s3`. M08 brings your own customer managed key;
- all four Block Public Access flags are `true`;
- object ownership is `BucketOwnerEnforced`: ACLs are switched off and the bucket owner owns every object;
- `DeletionPolicy` and `UpdateReplacePolicy` are both `Retain`. Deleting the stack, or a change that replaces the bucket, must not delete users' uploads.

The encryption block:

```yaml
BucketEncryption:
  ServerSideEncryptionConfiguration:
    - ServerSideEncryptionByDefault:
        SSEAlgorithm: aws:kms
      BucketKeyEnabled: true
```

## M04.2 — the assets bucket policy

A bucket policy is a resource policy: it lives on the bucket and names who may do what. The test renders your `AssetsBucketPolicy` and asks the course's policy evaluator. It checks that:

- `AssetsBucketPolicy` has `Bucket: !Ref AssetsBucket` and a `PolicyDocument`;
- statement `AllowAppUploads` lets the imported app role ARN do `s3:GetObject` and `s3:PutObject` on `${AssetsBucket.Arn}/uploads/*` (the role as `Principal: {AWS: …}`). The bucket policy alone allows it over HTTPS, and so does the whole evaluation of the role's identity policy (from M01) together with the bucket policy;
- statement `DenyInsecureTransport` denies everything over plain HTTP: `Effect: Deny`, `Principal: '*'`, `Action: 's3:*'`, a `Bool` condition `aws:SecureTransport: 'false'`, and **both** resources, the bucket ARN and the bucket ARN with `/*`. The evaluator must answer `ExplicitDeny` over HTTP, even for the app role, and also for `s3:ListBucket` on the bucket itself;
- nobody else gets in: an anonymous request and a role from another account are not allowed;
- the app is limited to `uploads/`: no read of `private/x.png` or `x.png`, and no `s3:DeleteObject`.

The TLS statement:

```yaml
- Sid: DenyInsecureTransport
  Effect: Deny
  Principal: '*'
  Action: 's3:*'
  Resource:
    - !GetAtt AssetsBucket.Arn
    - !Sub '${AssetsBucket.Arn}/*'
  Condition:
    Bool:
      aws:SecureTransport: 'false'
```

## M04.3 — old versions and unfinished uploads

Versioning keeps every overwrite, and every kept version is billed at the full price. The test reads the `LifecycleConfiguration` of `AssetsBucket` and replays it with the course's lifecycle model. It checks that:

- the rules are valid (the model rejects what S3 would reject);
- a rule with `Id: noncurrent-versions` exists and has `Status: Enabled`;
- it has `NoncurrentVersionExpiration` with `NoncurrentDays` between 1 and 90 (30 is a good start) and `NewerNoncurrentVersions` between 1 and 5 (3 is a good start);
- the replay: a version that has been noncurrent for 31 days with 3 newer noncurrent versions is deleted; with only 2 newer versions it is kept, however old; one noncurrent for only 10 days is kept;
- some rule has `AbortIncompleteMultipartUpload` with `DaysAfterInitiation` of 7 or less. The parts of an unfinished multipart upload are invisible in the console and billed until something deletes them.

One rule as an example:

```yaml
LifecycleConfiguration:
  Rules:
    - Id: noncurrent-versions
      Status: Enabled
      NoncurrentVersionExpiration:
        NoncurrentDays: 30
        NewerNoncurrentVersions: 3
      AbortIncompleteMultipartUpload:
        DaysAfterInitiation: 7
```

## M04.4 — the logs bucket

The ALB writes its access logs to a bucket, one small file every few minutes. The test checks that:

- `LogsBucket` is named `${Prefix}-logs-${AWS::AccountId}`;
- encryption is `AES256` (SSE-S3), **not** KMS. Load balancer access logs can only be delivered to a bucket that uses SSE-S3: with `aws:kms` the delivery fails and no logs arrive;
- all four Block Public Access flags are `true` and ownership is `BucketOwnerEnforced`;
- a lifecycle rule `alb-logs` with `Prefix: alb/` moves logs down by age: `STANDARD_IA` at 30 days, `GLACIER_IR` at 90, `DEEP_ARCHIVE` at 180. The model must say `STANDARD` at days 0 and 29, `STANDARD_IA` at 30 and 89, `GLACIER_IR` at 90 and 179, `DEEP_ARCHIVE` at 180;
- the rule expires logs after 730 days in `prod` and 365 days in `lab` (`ExpirationInDays: !If [IsProd, 730, 365]`). In both environments the expiry comes at least 180 days after the move to Deep Archive, because Deep Archive bills a 180-day minimum;
- the rule covers only `alb/`: a log under `other/` or `AWSLogs/` is left alone, even at 400 days;
- the rule also has `AbortIncompleteMultipartUpload` with `DaysAfterInitiation` of 7 or less;
- `LogsBucketPolicy` has `Bucket: !Ref LogsBucket`. Statement `AllowAlbLogDelivery` lets the principal `Service: logdelivery.elasticloadbalancing.amazonaws.com` do `s3:PutObject` on `${LogsBucket.Arn}/alb/AWSLogs/${AWS::AccountId}/*` and nothing else (not another account's prefix, not `alb/x.log`). The app role, a stranger and anonymous requests are not allowed to write;
- `DenyInsecureTransport` is in this policy too, with the bucket ARN and the bucket ARN with `/*`: over HTTP the answer is `ExplicitDeny`.

The delivered object keys look like `alb/AWSLogs/<account>/elasticloadbalancing/<region>/…`, which is why the policy names that prefix.

## Hints (read only when stuck)

- Why a Bucket Key? With SSE-KMS every object upload and download calls KMS, and KMS bills per request. A Bucket Key makes S3 ask KMS for one short-lived bucket-level key and use it for many objects, which cuts KMS request costs by up to 99 %. It applies to new objects only.
- Why SSE-S3 on the logs bucket? The log delivery service cannot use your KMS key, so access logs need a bucket with SSE-S3. This is a classic exam trap.
- The two-step minimum: you cannot move an object to another class before the first class's minimum storage duration has passed. Standard-IA bills a 30-day minimum, Glacier Instant Retrieval 90, Deep Archive 180. So the waterfall goes 30, 90, 180, and each step is at least the previous class's minimum later.
- `NewerNoncurrentVersions` needs `NoncurrentDays` next to it, and both must be exceeded before a version is deleted. Keep the count small: each kept version is a full-price copy.
- `${AssetsBucket.Arn}/*` is the objects; `AssetsBucket.Arn` alone is the bucket. `s3:ListBucket` acts on the bucket, `s3:GetObject` on objects. The TLS deny needs both, or `ListBucket` over HTTP slips through.
- `DeletionPolicy: Retain` sits next to `Type`, not inside `Properties`. When you delete the stack the bucket stays; empty it (all versions) and delete it by hand if you want it gone.
- `!If [IsProd, 730, 365]` gives a number, so it works for `ExpirationInDays`.
- `Env` and `Prefix` must be used somewhere or `cfn-lint` warns. `Prefix` goes in names; `Env` in the expiry.
- When a test fails, read its message first. It names the resource or the value that went wrong.

## Why this matters in the exam

- **Versioning and delete markers:** a delete on a versioned bucket only adds a delete marker; the data stays (and is billed) until a version is deleted. Lifecycle rules for noncurrent versions stop the pile-up.
- **Encryption:** every new object is encrypted with SSE-S3 by default. Choose SSE-KMS when you need key control and CloudTrail records; add a Bucket Key to cut KMS request charges.
- **Block Public Access and bucket owner enforced:** private by default; ACLs off. A bucket policy with `aws:SecureTransport` forces TLS.
- **Resource policy plus identity policy:** within one account either one allowing is enough; an explicit deny in either always wins.
- **Lifecycle:** transitions go down the waterfall (Standard, Standard-IA, Glacier Instant, Deep Archive) and respect minimum durations; abort incomplete multipart uploads; expire what you no longer need.
- **ALB access logs:** delivered to S3 by the log delivery service, which needs a bucket policy, and the bucket must use SSE-S3.
- **Cost:** S3 Standard is about 0.023 USD per GB-month for the first 50 TB (illustrative). Old versions, unfinished uploads and logs kept forever are the usual hidden cost.
